# 决策模型更正：离开网络 vs 网络本身变了

日期：2026-09-16
状态：三项决定已定（§11）；待你确认全文后进入实施计划
取代：`docs/2026-09-16-launchagent-design.md` 第 1 节、第 3 节的状态表与「离家」规则（触发层的机械部分不变：`WatchPaths` + `StartInterval` + 幂等收敛）

> 文档里的 `192.0.2.1`（特征设备）与 `192.0.2.100`（目标设备）取自 RFC 5737 留白段，只是示意。
> 本机真实值只写在 `~/.wifi-loc-control/locations.env` 里，不进仓库（`AGENTS.md` 第 8 节）。

## 1. 要纠正什么

现规则（`AGENTS.md` 约定 5）把**两种完全不同的处境**混成了一种：只要特征设备不可达，就一律「只通知、不回落」。

实测后果（2026-09-16）：把 Wi-Fi 切到手机热点后，位置停在 `Home`，那份静态配置让机器**完全没有网络**，而工具只弹一条通知；又因为 macOS 已无位置 UI，用户只能开终端敲 `scselect Automatic` 才能恢复。规则给了通知，没给能照着做的按钮。

正确的模型要把两件事分开：

| | 特征设备 | 目标设备 |
|---|---|---|
| 配置字段 | `LOCATION_n_IP` / `_MAC` | `LOCATION_n_TARGET_IP` / `_TARGET_MAC` |
| 回答的问题 | 我**在哪张**网络上？ | 这张网**还是我设置里期待的那张**吗？ |
| 不可达意味着 | 你已经不在这张网上了 | 你还在这张网上，但这张网变了 |
| 该做什么 | **回落到默认位置**，让机器在任何网络上都能用 | **通知**，不回落（别把静态设置悄悄换成 DHCP） |

特征设备这一侧，「**不可达**」与「**地址上换了设备**（MAC 不符）」视为同一件事：两种都说明这不再是那张网，都走回落。`broken` 因此只由一个原因触发——目标设备不可达。

## 2. 目标 / 非目标

**目标**：让「离开已知网络」自动回落到默认位置；同时保留「网络环境变了」时只提醒、不擅自动作的保护。

**非目标**：
- 不改二层探测机制（`/dev/udp` 触发 + `arp -n`，仍不用 ICMP / raw socket）。
- 不改「进入方向自动切换」——那条已经实测通过。
- 不做菜单栏（第 3 阶段）。
- 不做多目标设备（一个位置仍只支持一台目标设备）。

## 3. 配置格式与默认规则

```sh
LOCATION_1_NAME="Home"
LOCATION_1_IP="192.0.2.1"            # 特征设备：用来判断「我在哪张网上」
LOCATION_1_MAC="00:00:5e:00:53:01"

# 可选：目标设备，用来判断「这张网还是不是我设置里期待的那张」
# 省略时默认与特征设备相同
LOCATION_1_TARGET_IP="192.0.2.100"
LOCATION_1_TARGET_MAC="00:00:5e:00:53:02"
```

默认规则（按你的决定）：`_TARGET_IP` 缺省时取 `_IP`；`_TARGET_MAC` 缺省时取 `_MAC`。两者各自独立缺省，但通常一起给。

两个直接推论：

1. **默认下目标设备就是特征设备，两次检查必然同结论**，所以实现上**不要重复探测**——目标 IP/MAC 与特征 IP/MAC 相同时跳过第二次探测。
2. **`Home` 这种情况必须显式配置目标设备**，否则新功能永远不会触发（默认退化成特征设备自己）。现有那份线上配置需要补两行，否则行为与今天完全一样。

非法值与不完整组的处理沿用现状：缺 `NAME`/`IP`/`MAC` 的组跳过并记日志；`_TARGET_*` 单独缺失按默认规则补，不视为不完整。

## 4. 三个状态

按你的提议，`state` 文件从两态（`ok`/`away`）改成三态：

| 状态 | 含义 |
|---|---|
| `default` | 当前在默认位置（`Automatic`）。没有为该网络准备的静态设置，也就没什么可核对的 |
| `ok` | 当前在某个已知位置，**且目标设备在场**——设置与环境一致 |
| `broken` | 当前在某个已知位置，**但环境与设置不符**（目标设备不可达；或特征地址上换了别的设备） |

`state` 文件记两件事，各占一行：

```
state=ok                    # default | ok | broken —— §4 的三态
pending=feature-mismatch    # 只可能是这一条：欠着没送达的通知（见 §7）
```

`state` 记的是「我们在哪儿、以及就该位置告知过什么」；`pending` 记的是「还有一条通知没送到用户手上」。两者分开，是为了让 `state` 保持如实——位置真的切了就写 `default`，不能因为通知投递失败而写成「还在别处」。

（早期版本在这里多存一个 `miss` 计数器，供跨轮安全阀使用；§8 把确认搬进轮内之后已经删掉。读到 `miss=` 行按「未收到过通知」处理，见 §10 的 N11。）

沿用约定 12 的语义：`ok` / `default` 一律重置；只有**真的送达**了才写 `broken`。旧格式（单行 `ok`/`away`）按「未知值 = 没收到过通知」处理（现有失败方向），**不需要迁移脚本**。

## 5. 完整转移表

`F` = 特征设备（地址 + MAC 双匹配），`T` = 目标设备，`cur` = 当前位置，`L` = 命中的位置，`D` = 默认位置。

| # | 特征 `F` | 目标 `T` | `cur` | 动作 | 新状态 | 通知 |
|---|---|---|---|---|---|---|
| 1 | 命中 | 在场 | `cur == L` | 无 | `ok` | — |
| 2 | 命中 | 不可达 | `cur == L` | 无（不动设置） | `broken` | **进入 `broken` 时一次** |
| 3 | 命中 | 在场 | `cur != L` | **切到 `L`**，然后核对 `T` | `ok` | — |
| 4 | 命中 | 不可达 | `cur != L` | **切到 `L`**，然后核对 `T` | `broken` | 同上 |
| 5 | 未确认 | — | `cur == D` | 无（已经是默认位置） | `default` | — |
| 6 | 未确认 | — | `cur != D` | **第一遍扫描未命中就回落到 `D`**，剩余扫描就地继续，再走 §8 的末次复探 | 见 §8 | 见 §7 |

「未确认」= 特征设备不可达，**或**其特征地址上换了设备（MAC 不符）。两者同路，见 §1。

两台设备都按约定 4 做**地址 + MAC 双匹配**，动作由**角色**决定：特征设备只要不是「双匹配通过」就算「不在这张网上」（回落）；目标设备只要不是「双匹配通过」就算「这张网变了」（`broken` + 通知）。

第 3/4 行体现你的顺序决定：**先切换、再核对目标设备**——先把机器放到能用的配置上，网络一切正常时用户立刻就能用；有问题才提醒。

第 6 行是**先走后核，而且决策提前**：第一遍扫描（每条规则各一次尝试）没有命中就立刻回落，不等满预算——默认位置是 DHCP，机器马上就有网；剩下的预算不丢，就地继续扫（命中就静默切回），之后 §8 再做一次末次复探。

## 6. 与既有约定的关系

- **约定 5 重写**（原文见附录）：
  > **自动化做两个方向，且只有「离开」会自动回落到默认位置。** 进入已知位置是自动的；发现已经不在这张网上（特征设备未确认）时**立即**回落到默认位置——默认位置就是 DHCP，在哪儿都能用——并在同一轮里复探一次确认：复探命中就静默切回，仍不命中就静默留下；而**在某个已知位置内发现目标设备不符时（目标设备未确认），只通知、不回落**——那种改动应当由人确认。
- **约定 4（IP + MAC 双匹配）沿用**，并扩展到目标设备：目标地址上换了设备也算不符。
- **约定 6（幂等）**：回落同样受它约束。回落写入 `SystemConfiguration` 会再触发一轮，那一轮读 `cur == D` + `F` 不可达 → 无动作，收敛。
- **约定 12（去重语义）**：不变，但状态词汇换成 `default`/`ok`/`broken`。
- **约定 2（不需要 root）**：不变，回落仍是 `scselect`。

## 7. 通知策略

- **进入 `broken`**：通知一次（目标设备不可达或已换设备——设置与当前网络环境不符）。停留在 `broken` 不重复。
- **确认离开**（复探仍不命中）：**不通知**。机器已经自己切到默认位置并且能用，而这是每一次离家都会发生的事，通知只会变成噪音。原因与时间戳只进本地日志。
- **特征地址上换了设备**（MAC 不符）：回落 + **通知一次**。这才是真正的「网络环境变了」（例如家里换了路由器），也是唯一不该被静默盖掉的情形。
  - **投递失败时记为「欠着」**：`state=default`（位置如实）+ `pending=feature-mismatch`。下一次能观察到同一异常（当前在默认位置、该地址上仍是别的设备）的轮次重试，送达后清空；观察不到就保留。`state` 不因此写成别的值——否则要么骗了位置，要么会抑制以后的目标设备通知。
- **假性缺席**（复探命中、静默切回）：**不通知**。
- 其余转换（进入 `ok`、进入 `default`）不通知。
- 所有通知文案沿用隐私约定：不含 SSID、不含地址、不含 MAC。

## 8. 轮内确认：决策提前，预算不变（2026-09-16 晚间二次改定）

**第一遍扫描未命中就立即回落到默认位置，不等满探测预算。预算本身不缩短——剩余扫描就地继续（命中就静默切回），仍不命中再等 15 秒做最后一次复探。**

一次「扫描」（sweep）= 每条规则各做一次尝试；一次尝试 = 查邻居表 → 条目缺失就发包 → 等 `RETRY_DELAY` 再查一次。

| | 改前 | 改后 |
|---|---|---|
| 回落时刻 | 满 4 次尝试之后（实测 7.7 秒） | **第一遍扫描之后（实测约 1.3 秒）** |
| 探测总量 | 4 次 + 末次 4 次 = 8 次 | **不变：4 遍扫描 + 末次 4 遍** |
| 复探命中后的切回 | 15 秒窗口之后 | 之后，或更早（剩余扫描里命中就当场切回） |

为什么可以这样提前（2026-09-16 实测）：

1. **回落决策本身没有延迟。** 真实一轮（`15:51:48`）里，`no answer` 之后立刻就是 `scselect`；7.7 秒全部花在「把 4 次尝试走完」上，而这段时间机器一直停在不适配的静态配置上。
2. **首次尝试内部已经含「发包 + 等 1 秒 + 再查」。** 邻居表条目自然老化时，这一发就会把它填回来，所以提前判定不会把「条目老化」误判成离开。
3. **误判的代价仍然有界。** 剩余扫描与末次复探都能切回，暴露窗口从 7.7 秒缩到 1.3 秒；代价仍是两次接口重配，使用者已判定可接受。

不变式：**真离开时整轮耗时不变**（仍是 8 次尝试 + 15 秒等待），因为预算没动，只是决策点前移；用户能感知的「停在不合适的位置上」的时间从 ~7.7 秒降到 ~1.3 秒。

**不提前的两处**：进入方向（`cur == D` 时找已知网络）与目标设备核对仍走满预算。那两处一次判定定生死——误判要么错过进入、要么把 `broken` 报错——没有「便宜的重试」可用（§9）。

## 9. 失败模式

| 情况 | 行为 |
|---|---|
| `locations.env` 缺失或所有组非法 | 退出 3，不切换不通知（现状） |
| **当前位置读不出来**（`scselect` 失败，或输出不再是本脚本认识的形状） | **退出 1，一次 `scselect` 都不调用**，只记一行日志。位置值是「要不要调 `scselect`」的唯一依据，而每次 `scselect` 都会重写 `SystemConfiguration` 并触发下一轮——猜着走会变成每分钟一轮的切换循环（实测：连切到当前位置都会重写） |
| **配置里的地址写法有歧义**（前导零、`0.0.0.0`、多播） | 该组跳过并记日志。实测 `arp` 把前导零当八进制（`198.51.100.010` → `198.51.100.8`），`0.0.0.0` 会返回网关条目（在哪个网络都能匹配上网关 MAC） |
| 目标设备只是短暂无响应 | 探测本身有 4 次 × 1 秒重试；仍失败则进入 `broken` 并通知一次 |
| 回落时 `scselect` 失败 | 退出 1 并记日志（现状） |
| 通知发送失败 | 不写 `broken`，下一轮重试（约定 12）；「换了设备」那条改记 `pending=`（§7） |
| 只有特征设备、没配目标设备 | 目标恒等于特征，第 2/4 行不可达——**行为与今天一致**，属于向后兼容 |

| N13 | 第一遍扫描未命中（`cur != D`），设备在**剩余扫描**里回答 | **不等满预算就回落**，并在剩余扫描内**静默切回**（两次 `scselect`），不通知，`state=ok`；整轮耗时明显短于确认窗口 |
| N14 | 设备全程无应答 | 探测预算不变（4 遍扫描 + 末次 4 遍，实测约 14 秒），但**回落决策落在运行开始后 3 秒内** |
| N15 | 当前位置读不出来（`scselect` 失败 / 输出变形） | 退出 1、**一次 `scselect` 都不调用**、记一行日志；不得当成「不在默认位置」 |

| N17 | 「换了设备」那条通知投递失败 | `state=default` + `pending=feature-mismatch`；下一次可观察时重试，送达后清空 |

端到端（真实系统）：热点场景应在**约 1–2 秒**内自动回落到 `Automatic`（第一遍扫描即判定；随后剩余扫描与 15 秒末次复探只负责「万一只是抖动」），**不再需要手动敲 `scselect`**，也**不再弹通知**；回家后应自动切回 `Home`。**2026-09-16 16:15–16:16 已实测确认**：网络变化到 `switched to 'Automatic'` 约 2 秒，整轮走完 `we have left`（真实环境首例）且 0 通知；回家一轮内切回 `Home`、目标在场、`state=ok`。

### 11.2 实际使用复核后改定的三件事（2026-09-16）

1. **安全阀从「跨轮两轮」改为「轮内确认一次」**（§8）。跨轮意味着每次真实离开都要多等 60–74 秒的无网时间，而它防的主要风险——「自己切换清空邻居表」——实测不成立。
2. **确认离开时不通知**（§7）。回落之后机器已经自己可用，而这是每次离家都会发生的事。
3. **去掉 `StartInterval`**（§12），并把手动切换命令写进 README 作为错误时的出口。

推动这次改动的是使用者对**需求本质的更正**：真实场景是「连接一个网络」而不是「在两个网络之间反复切换」，所以「自动化导致位置反复切换」的担忧被高估了——那个印象来自测试中反复 `scselect` 造成的振荡。同时 `Automatic`（DHCP）本身是安全落脚点，**过早回落的代价远小于过晚回落**。

### 11.3 首次真实轮内复探之后改定的一件事（2026-09-16 晚）

`15:51:48` 的真实一轮（使用者连上热点、随后很快连回家里的 Wi-Fi）证明：**回落决策本身没有延迟，7.7 秒全部花在走完 4 次尝试上**，而这 7.7 秒里机器一直停在不适配的静态配置上。使用者因此提出把「决策点」与「探测总量」拆开。按此改定为 §8：第一遍扫描未命中就回落，预算原样走完，只是切换的决策提前。桩覆盖见 N13/N14；**2026-09-16 16:15 的真实一轮已确认**：从网络变化到 `switched to 'Automatic'` 约 2 秒（旧路径约 9–10 秒），随后整轮走完 `we have left`、全程 0 通知。

其余细节（字段名、状态名、文案措辞）按本文档执行，实施中若发现需要偏离，先回来改这里。

### 11.4 触发限速：保持 `ThrottleInterval` 60 秒（2026-09-16 晚）

看完实测数据后决定**不动** `ThrottleInterval`（仓库与已安装的 plist 里都仍是 60）。依据：

- 日志里 119 个「相邻两轮启动」的间隔，**最小值恰好 60 秒**——下限真实生效（launchd 默认是 10 秒）；事件成串时被摊成 60/61 秒一轮（`18:22:52 → 18:23:52 → 18:24:53`）。
- 三次人工切网的**前置间隔**分别是 121 秒、1341 秒、83 秒，**都没落进窗口**——这不是运气：agent 平时空闲，而切网本身就是那个事件。
- 真正会把间隔压进 60 秒的，是「一轮日常噪音刚跑完、紧接着切网」这种巧合：安静期实测每 2–15 分钟一轮，粗估这种巧合约 20%，代价是最多多等一分钟。
- 降它的代价是确定的：单轮离开要跑 31 秒，降到 20 秒必然出现重叠运行（状态文件是原子写、判定幂等，所以代码能忍，但日志会交错、切换动作可能重复）。

**这条尾风险明确接受**，记录在此以免后来者为了「更快」去动它——把感知延迟从 9–10 秒砍到 2 秒的是 §8 的决策提前，不是这个键。将来真要封尾，先做一次定向实测（制造一轮噪音事件后立刻切网，量出推迟量），不要凭直觉改数字。

## 12. 触发集合与手动出口

**去掉 `StartInterval`。** 触发只剩 `RunAtLoad`（装载/登录时各一次）与 `WatchPaths`（`/Library/Preferences/SystemConfiguration` 有变化）。理由是使用者要的是「网络环境变化时被激活的、只跑一轮的脚本」，而不是周期性轮询；去掉之后安静期不再有空跑，日志只在网络活动时增长。

代价必须一起接受：**`WatchPaths` 漏一次事件，位置就会一直停在错的上面，直到下一次网络变化。** 而 `man launchd.plist` 明说 `WatchPaths` 会漏事件，所以手动出口不是可选项，必须在 README 里写清楚：

```sh
networksetup -listlocations     # 有哪些位置、当前是哪个
scselect                        # 当前位置（简写）
scselect <位置名>               # 手动切换
```

（路线图第 3 阶段的菜单栏就是把这个做成能点的按钮；在那之前这三行是唯一入口。）

### 约定 5（2026-09-16 已被替换）

> **自动化只做「进入」方向。** 从 `Automatic` 切到识别出的位置是自动的；从非默认位置退出**只通知、不自动切**。理由是二层层面「设备消失」可能意味着真实配置变动，不该由脚本猜。

### §8「轮内确认」（2026-09-16 下午版，当晚被 §8 取代）

> **首轮未确认就立即回落到默认位置，然后在同一轮里等 15 秒复探一次。** 复探命中 → 静默切回原位置；仍不命中 → 确认离开，静默留在默认位置。
>
> 为什么可以这么激进（2026-09-16 复核后的结论）：
>
> 1. **默认位置是安全落脚点。** `Automatic` 就是 DHCP，几乎所有网络都能用；所以「过早回落」的代价只是这一轮里多一次接口重配（实测切换瞬断很短、体感隐蔽），**不是断网**。
> 2. **回落可逆、代价有界。** 判断错了就在同一轮里切回来，暴露窗口是 15 秒，而不是跨轮方案的 60–74 秒。
> 3. **「自己切换会清空邻居表」已不构成威胁。** 实测复核：切换之后那一轮探测会自己重新发包，**1–3 秒内就命中**，不会误报缺席。原先把它当作安全阀的主要理由，是**测试中反复 `scselect` 造成的振荡**带偏的——真实使用不会那样切网。
> 4. **单次抖动仍被覆盖**：`10:49:38` 那次持续 8 秒，15 秒的复探窗口包得住。
>
> 代价（明确记下）：假性缺席时是**两次**接口重配（回落 + 切回），而不是零次。使用者已判定可接受。
>
> 这条同时**去掉 `state` 文件里的 `miss` 计数器**——确认从跨轮搬进轮内之后，状态文件只剩 `state=` 一行。
